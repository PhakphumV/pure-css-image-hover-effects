## 02. Variant and duplicate analysis

Variants are intentional (different direction, different timing,
different axis). Duplicates would be visually indistinguishable. The
analysis below classifies each group.

### Intentional variants (RETAIN)

| Group | Category | Slugs | Distinction |
|-------|----------|-------|-------------|
| flip | 3d | flip-horizontal, flip-vertical | different flip axis |
| radial | overlay | radial-in, radial-out | different reveal direction |
| rectangle | overlay | rectangle-in, rectangle-out | different reveal direction |
| bounce | pan | bounce-bottom, bounce-left, bounce-right, bounce-top | different bounce direction |
| zoom | zoom | zoom-in, zoom-out | opposite zoom directions |
| zoom-pan | composite | horizontal-zoom-n-pan, vertical-zoom-n-pan | different pan axes |
| shadow | shadow | shadow-drop, shadow-lift | different shadow direction |
| contrast | filter | contrast-punch, contrast-soften | increase vs. decrease contrast |
| glitch | reveal | glitch-shift, glitch-slice | RGB-channel shift vs. slice animation |
| tilt | 3d | magnetic-tilt, parallax-tilt | different glare position (both rewritten as 3d tilt in #34) |
| slide | pan/zoom | slide-reveal, slide-reveal-right | slide direction |

### Timing/speed variants (RETAIN)

| Slug | Relationship |
|------|-------------|
| zoom-in-slowmo | slow-timing variant of zoom-in |

### Glitch variants (RETAIN)

Both `glitch-shift` and `glitch-slice` use `clip-path` animation
but with different visual intent (RGB shift vs. horizontal slicing).
Their descriptions make this distinction explicit.

### Duplicates found

**None.** Every pair of similarly-named effects has a meaningful,
visible distinction documented in its `meta.json` description.

## 03. Taxonomy review

The 13-category taxonomy is:

- Understandable to users (zoom, pan, 3d, filter, etc. are intuitive)
- Mutually meaningful (zoom ≠ pan ≠ 3d; reveal ≠ overlay)
- Stable (categories have existed since the schema)
- Consistently represented in `meta.json`, the schema, the
  README, and the catalog
- Not dependent on implementation details

### Concerns

- **`distortion` has only 1 effect** (liquid-morph). Borderline
  but the visual behavior (morphing border-radius) is genuinely
  different from every other category.
- **`fade` has only 1 effect** (corner-frame). Same situation.
  These single-effect categories are acceptable per the schema
  ("Adding a new category requires a schema version bump") and
  give consumers more precise labels.

### No merges needed

Every effect in a single-effect category represents a genuinely
distinct visual concept. Merging would lose information.

## 07. Catalog and build-system cleanup

`scripts/build_catalog.py`:
- Reads `effects/*/meta.json` as the source of truth
- Hardcodes `FEATURED_SLUGS = ["zoom-in", "shine-sweep", "glitch-shift"]`
  (intentionally curated; documented in code)
- Generates hero, filter pills, sections, and cards from metadata
- Output is byte-deterministic (verified by CI)

`styles/catalog.css`:
- Has hardcoded `body:has(input[name="cat"][value="X"]:checked)`
  selectors for each of the 13 categories. This is a known
  limitation — adding a 14th category would require adding a
  selector here. Documented as a follow-up optimization.

### New validator check

Added `check_catalog_featured_slugs()` to the validator. It parses
`FEATURED_SLUGS` from `build_catalog.py` and verifies:
1. Every featured slug has a corresponding `effects/<slug>/`
   directory.
2. Every featured slug passes the per-effect validation.

This prevents a stale featured list from breaking the catalog.

## 08. Gallery CSS and category filtering

The category filter uses `body:has(input[name="cat"][value="X"]:checked)`
to hide non-matching cards. This is:

- JS-free (contract §1)
- Supported in Chrome 105+, Edge 105+, Firefox 121+, Safari 15.4+
  (documented in BROWSER_SUPPORT.md)
- Hardcoded per category in `styles/catalog.css`

**Known limitation:** adding a new category requires adding a
new selector rule. The category metadata is in `meta.json`; the
filter CSS is in `catalog.css`. A future improvement could generate
the filter CSS from the schema's category enum, but this is out of
scope for #37.

## 11. Template and contributor workflow

`effects/_template/` contains:
- `effect.css` — uses `.hover-effect.<effect-class>` selectors
- `index.html` — canonical markup (no `tabindex` after #35)
- `meta.json` — all required fields with placeholders

`CONTRIBUTING.md` (updated in #17) describes the 4-step workflow:
1. Copy the template
2. Edit the three files
3. Run the validator
4. Run the catalog builder

The template is consistent with the contract, schema, and validator.

## 12. Automated consistency checks

In addition to the per-effect checks from #33, the validator now
runs three repo-level checks:

- `check_base_css()` — verifies `styles/base.css` contains the
  a11y guards (added in #35)
- `check_catalog_featured_slugs()` — verifies featured slugs in
  `build_catalog.py` exist and pass validation (added in #37)
- Fixture suite (`--check-fixtures`) — verifies the validator
  itself against 11 known-good and known-bad fixtures (added in
  #33)

These checks run on every push to main and every PR.

## 13. Recommendations

1. **No effect merges.** Every pair of similarly-named effects has
   a meaningful, documented distinction.
2. **No effect retirements.** All 54 effects pass validation and
   serve a distinct visual concept.
3. **Catalog filter CSS** could be generated from the schema's
   category enum. Tracked as a future optimization.
4. **Browser automation** (Playwright or similar) would enable
   real visual regression testing. Tracked in #36 as a
   follow-up.
5. **3 empty categories** (`border`, `rotate`, `distortion` was
   added) are intentionally retained in the schema. Removing
   them would be churn without value.
